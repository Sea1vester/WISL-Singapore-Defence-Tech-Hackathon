How does data actually move? (read this first)

Your laptop is not a cloud during dev. You are not uploading JSON to the internet. You run a small web server on your Mac that receives JSON and saves it to a local file (SQLite).

The three pieces (not just a database)

1. API (the door)

FastAPI web server on :8000. Teammate knocks on this door with HTTP POST. They never touch the database file directly.

2. SQLite (the filing cabinet)

A file on disk: ./data/telemetry.db. Only your API reads/writes it. Not shared on the network by itself.

3. LLM worker (the translator)

Reads raw JSON from SQLite, calls Ollama, writes canonical JSON back to SQLite. Also triggered via your API/queue.

Common misconceptions - answered

Do I upload JSON somewhere?

On your Mac (now): No upload to the cloud. You run curl -X POST http://localhost:8000/v1/telemetry/ingest -d @sample.json and the API saves it locally.

Later on Azure: Teammate POSTs to your public API URL. The API saves to SQLite on the VM. Still not "upload to a database" - they hit your API, which owns the database.

Do I need a domain?

Local dev: No. localhost:8000 is enough.

Azure demo: A domain is nice for HTTPS but not required. A public IP like https://20.x.x.x works (or IP + Caddy self-signed for dev).

You need an address teammates can reach over the internet, not necessarily a custom domain.

Can teammates just access the database?

No - and you should not let them. SQLite is a local file. Exposing it directly would be insecure and awkward.

Instead you give them API endpoints:

  • POST /v1/telemetry/ingest - teammate sends normalized JSON in
  • GET /v1/flights/{id}/records - anyone authorized reads canonical JSON out
How does the raw telemetry guy send to my Mac?

During Mac-only dev: He usually doesn't. You fake his payloads. If you must test early, use Tailscale so his machine can reach http://your-mac:8000 on a private tunnel.

For real integration: His parser converts raw telemetry to JSON, then runs something like:

curl -X POST https://YOUR-API-URL/v1/telemetry/ingest \
  -H "Authorization: Bearer TELEMETRY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"flight_id":"...","records":[...]}'

His code does an HTTP request. Your API receives it. Done.

One sentence summary: You build a web API that accepts JSON and stores it; teammates call that API over HTTP; SQLite is just where your API keeps the data on disk.

Cloud platform (what you always need)

Azure is the platform: networking, identity, storage, managed services, billing, region (Singapore). Your teammate POSTs to a URL hosted on Azure either way.

  • Resource group, region, budget alerts
  • Key Vault for API keys
  • Blob Storage for backups / exports
  • Container Registry for images
  • TLS, DNS, monitoring

VM (one compute choice on that platform)

A VM is not a different cloud - it is a rented Linux server inside Azure. We picked it because two plan choices are awkward on serverless PaaS:

  • Local DeepSeek via Ollama - wants ~16 GB RAM and a persistent model cache
  • SQLite file on disk - wants a mounted volume, not ephemeral container storage

If you drop the VM, what changes?

You gain (platform-native)

  • No SSH, patching, or deallocating a server
  • Autoscale ingest workers independently
  • Managed DB backups and HA options
  • Closer to how GCC production systems are built

You give up or rework

  • Local Ollama - replace with DeepSeek API or Azure OpenAI (cost + API key)
  • SQLite file - move to PostgreSQL or store JSON in Blob + index elsewhere
  • docker-compose parity - split into separate Azure resources + IaC (Bicep/Terraform)
  • Student $100 budget - managed DB + Container Apps can burn credit faster than a stopped VM

Phase 0 - Data contract (do this first)

You do not know the final telemetry shape yet. Do not hard-code a schema until you and your teammate agree on an ingestion contract. Everything downstream depends on this.

Layer Owner Format Purpose
L0 Raw Teammate Unknown binary / vendor-specific Not your problem
L1 Normalized Teammate delivers JSON or CSV with documented fields Your ingestion input
L2 Canonical Your LLM pipeline Strict JSON Schema Stable API for apps and analytics
L3 Storage Your SQLite DB Tables + JSON columns Queryable history + audit trail

Minimum contract to agree with teammate

Delivery: HTTPS POST to /v1/telemetry/ingest
Auth: API key header or mutual TLS (pick one)
Payload: JSON object with flight_id, timestamp_utc, source, records[]
records[]: flexible key-value map (teammate's normalized fields)
Idempotency: optional client-supplied event_id to dedupe retries

Suggested canonical JSON Schema (L2 - you define)

{
  "flight_id": "uuid",
  "timestamp_utc": "ISO-8601",
  "position": { "lat": 0.0, "lon": 0.0, "alt_m": 0.0 },
  "attitude": { "roll_deg": 0, "pitch_deg": 0, "yaw_deg": 0 },
  "battery": { "percent": 0, "voltage_v": 0 },
  "sensors": { "...": "extensible" },
  "metadata": { "drone_model": "", "firmware": "" }
}

The LLM's job: map arbitrary L1 fields into this L2 shape, flag unknown fields in a sensors.extra bucket, and never silently drop data.

SQLite schema (starter)

Store both raw normalized input and LLM output for auditability and re-processing.

-- flights: one row per flight session
CREATE TABLE flights (
  id            TEXT PRIMARY KEY,
  source        TEXT NOT NULL,
  started_at    TEXT NOT NULL,
  ended_at      TEXT,
  created_at    TEXT DEFAULT (datetime('now'))
);

-- ingest_events: raw L1 payloads as received
CREATE TABLE ingest_events (
  id            TEXT PRIMARY KEY,
  flight_id     TEXT REFERENCES flights(id),
  received_at   TEXT DEFAULT (datetime('now')),
  payload_json  TEXT NOT NULL,
  idempotency_key TEXT UNIQUE
);

-- canonical_records: L2 output from LLM
CREATE TABLE canonical_records (
  id            TEXT PRIMARY KEY,
  ingest_id     TEXT REFERENCES ingest_events(id),
  flight_id     TEXT REFERENCES flights(id),
  recorded_at   TEXT NOT NULL,
  canonical_json TEXT NOT NULL,
  llm_model     TEXT,
  llm_latency_ms INTEGER,
  validation_ok INTEGER DEFAULT 0
);

-- translation_jobs: async pipeline state
CREATE TABLE translation_jobs (
  id            TEXT PRIMARY KEY,
  ingest_id     TEXT REFERENCES ingest_events(id),
  status        TEXT CHECK(status IN ('pending','running','done','failed')),
  error         TEXT,
  created_at    TEXT DEFAULT (datetime('now')),
  updated_at    TEXT
);

CREATE INDEX idx_canonical_flight_time ON canonical_records(flight_id, recorded_at);
CREATE INDEX idx_jobs_status ON translation_jobs(status);

Risks and mitigations

Schema unknown until teammate delivers

Mitigation: contract-first OpenAPI; store raw L1 always; LLM handles field mapping flexibly.

LLM hallucination / invalid JSON

Mitigation: JSON Schema validation, retry with repair prompt, human-review queue for failures.

SQLite single-writer bottleneck

Mitigation: batch writes, WAL mode, async translation; plan PostgreSQL migration path if >50 writes/sec sustained.

Azure credits run out before demo

Mitigation: Mac-only until last month; deallocate VM when not demoing; set $80 budget alert; only allocate B4ms for integration/demo weeks.

High telemetry rate (10+ Hz per drone)

Mitigation: teammate batches records; you ingest batches not single points; size queue and worker count accordingly.
